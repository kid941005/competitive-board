# v1.3.0 — 市场消息看板、手工补录与原文链接解析（第一部分）

本版补上第一部分的**友商市场消息看板**：订阅 RSS/Atom 源，后台定时抓取入库，
页面按发布时间倒序排成按天分组的单列时间线（版式参考 aihot.news），滚到底自动加载下一页。
同时支持**手工补录**（贴链接入时间线），并把 Google News 检索源的**跳转链接解析成真实原文地址**。
数据库升到 **schema v9**（v8 新增 `news_sources` / `news_items` 两张表；v9 给 `news_items` 加 `real_url` 列），
启动时自动迁移，无需手工操作。

> 本版为功能版本：GitHub Release 的 Latest 与容器镜像 `latest` 均指向 `1.3.0`。
> 回滚到 1.0.8 前请先备份数据卷 —— v8/v9 的新闻表与 `real_url` 列在 1.0.8 里不存在，旧代码会忽略它们，
> 但迁移版本号高于代码会**拒绝启动**（`SchemaTooNew`）。

## 主要修改

### 高：新功能

- **市场消息看板 `/news`**：单列按天分组的时间线，按 `published_at` 倒序；
  日期组头显示「11月27日 星期五 · N 条」并可折叠，每条左侧是本地时刻与时间轴圆点，
  右侧卡片带来源、公司标签、标题、摘要、原文链接；顶栏筛选按**公司 / 来源 / 关键词**。
  分组按**本地时区**切（22:00 UTC 的消息在北京时间是次日，按 UTC 分组会和卡片上的时刻对不上）。
- **无限滚动**：`IntersectionObserver` 在距底部约 600px 时取下一页，`GET /news/items` 返回
  服务端渲染好的卡片片段；老浏览器自动退回「加载更多」按钮。
- **游标分页**：按 `(published_at, id)` 做游标，而不是 offset —— 翻页期间新消息插到最前面时
  offset 会整体错位，导致重复或漏条。游标是 `微秒时间戳|id` 的整数对（ISO 串里的 `+`
  在查询串会被解成空格，没做 URL 转义的调用方会静默拿回第一页）。
- **消息源管理 `/admin/news`**：增删改订阅源（名称 / URL / 公司 / 语言 / 启用状态）、
  单个刷新与全部刷新、显示每个源的上次抓取时间、状态码、错误原因、成功/失败计数。
- **自动抓取**：`lifespan` 内起后台任务，间隔由系统设置 **市场消息自动抓取间隔 (分钟)**
  （`news.refresh_minutes`，默认 60，`0` 关闭）决定，改完下一轮生效；关闭时 `finally`
  里 cancel，不留悬挂任务。
- **内置 11 个订阅源**：首次启动自动预置（村田 / xMEMS / Frore / 巴特尔斯等的新闻与 IR 页），
  表非空就不再动它。

### 高：手工补录（贴链接入消息）

- **为什么要它**：微信没有公开 RSS（不能订阅别人的公众号），行业里也有不少站点根本不出 feed。
  与其自建 RSSHub / 逆向微信协议（合规风险高、登录态会过期），不如让用户把文章链接贴进来。
- **页面 `GET /news/clip`**（需 `data:write`）：一行一条链接，每批最多 12 条，可统一挂到一家公司；
  提交后**同步**抓取并当场显示结果（新增 / 重复 / 失败三栏 + 每条标题、发布时间、原文链接）。
- **只取公开页面的标题、一句摘要、发布时间**，不抓正文（时间线只需要这些，正文涉及版权与体积，
  想看全文点「原文」跳过去）；页面上确实没有发布时间时用抓取时间入库（宁可时间偏晚，也不让一条消息沉底）。
- **猜字段的优先级固定写在代码里**（`app/news_clip.py`）：标题 `og:title` → `twitter:title` → `<title>` → `<h1>`；
  摘要 `description` → `og:description` → `twitter:description` → 公众号 `#js_content` 截断；
  时间「公众号 `var ct` 秒级时间戳 → `article:published_time` / `og:release_date` / `publishdate` / `pubdate`
  → JSON-LD `datePublished` / `<time datetime>`」。猜不到就留空，不编造。
- **同一条链接不会重复入库**：补录条目与 RSS 条目共用 `dedupe_key`（`sha1(归一化链接)`，去 utm 参数与锚点），
  所以「先补录、后订阅到」或反过来都只留一条。
- **补录挂在一条固定源上**（`name=手工补录`、`url=manual://clip`、`kind=manual`）：时间线需要 `source_id`，
  按来源筛选时也能单独看到。这条源**没有 feed 地址，自动抓取会跳过它**，管理页里也只显示为只读行、没有「抓取」按钮。
- **抓取边界**：单条 8 秒超时、整批 10 秒总预算（超时的链接直接判失败并列出原因），并发 6 条；
  页面超过 2 MB 跳过；只接受 `http(s)` 链接。某一条失败不影响同批其它链接。

### 高：原文链接解析（Google News 跳转页 → 真实地址）

- **问题**：内置 7 个 Google News 检索源吐出的 `<link>` 是 `https://news.google.com/rss/articles/CBMi…?oc=5`
  这种跳转页（演示库里 567 条有 507 条是它），点「原文」可能打不开。实测：该页 GET 返回 200 但不 302，
  HTML 里没有原文 URL，新格式 id 的 base64 也解不出明文，跟随重定向与本地解码都不可行。
- **解法**（`app/news_link.py`）：GET 文章页取 `data-n-a-sg` / `data-n-a-ts` 签名 →
  POST `https://news.google.com/_/DotsSplashUi/data/batchexecute`（`f.req` 带 `Fbv4je` + `garturlreq`）→
  从返回的 `garturlres` 里取真实 URL。这是 Google 页面前端自用的接口，**不保证永久可用**，失效就回落原链接。
- **按需解析 + 缓存**：卡片「原文」指向新路由 `GET /news/item/{id}/go`，已缓存 `real_url` 就 302 到真实地址；
  没缓存就当场解一次（约 1–3 秒）并写回 `news_items.real_url`。schema **v8 → v9** 就是加这一列。
- **后台回填**：启动时与每轮自动抓取后各起一个后台线程（`news_link.backfill_async()`，防重入闸门），
  把存量 `real_url IS NULL` 的 Google 条目逐条补上（每批 40 条、并发 6），不阻塞请求与启动。
- **失败不制造死链**：解析失败（页面改版 / 网络不通）保留原 Google 链接，卡片照常可点。
- 其余来源（官网 RSS、手工补录）本来就是真实链接，`resolve_url` 原样返回，不受影响。

### 高：SQLite 并发写锁修复

- Docker 实测发现：抓取期间并发写请求偶发 500（`sqlite3.OperationalError: database is locked`）或卡 20–120 秒。两个根因：
  1. `get_session` 的写锁原用 `threading.RLock()`；FastAPI 的 yield 依赖 acquire 与 finally release 可能落在 anyio 线程池的不同线程，跨线程 release 抛 `RuntimeError: cannot release un-acquired lock`，锁计数泄漏后所有写请求永久阻塞。改为普通 `threading.Lock()` + `acquire(timeout=30)`，用标志记录本请求是否拿到，finally 按标志释放。
  2. 抓取把网络 IO 放在请求事务里：一个 10 秒超时的源会把全站写请求一起堵住。改为「先读计划并 commit 结束只读事务 → 网络/解析在锁外 → 仅入库那一下进写锁」；手动全量刷新改走独立后台线程（`news.refresh_background()`，带防重入闸门），不再挂在请求作用域里。
- 连接层补 `busy_timeout=30000`、`timeout=30`，`journal_mode=WAL` 只在 `init_db()` 里设一次。
- 已知取舍：管理页单源刷新仍同步执行（用户要马上看到结果），最坏把其它写请求挡一次抓取时长（实测 1–3 秒，超时上限 10 秒）；全量刷新与自动抓取不占请求锁。
- 实测：3 线程每 0.5 秒登录、持续 40 秒，并每轮触发全量刷新 —— 209 次请求全部 303、最慢 0.17 秒，无 5xx、无 Traceback；单源刷新 1.6 / 2.6 / 1.2 秒。

### 中：抓取与解析的边界

- 抓取用**标准库 `urllib`**（`app/news_fetch.py`），不引入 `feedparser` / `httpx`，后端依赖表不变；
  条件请求带 `If-None-Match` / `If-Modified-Since`，304 直接标记成功不重复入库。
- 解析前**拒绝带 DOCTYPE 的 XML**：`xml.etree` 会展开外部实体，订阅源是外部输入，必须先挡 XXE。
- 单次响应上限 4 MB、单次最多 200 条；标题截 300 字、摘要截 400 字并去 HTML。
- 时间解析同时认 RFC 822（RSS）与 ISO 8601（Atom），统一转 UTC 入库，渲染走 `localtime`。
- 去重键 `dedupe_key` = `sha1(归一化链接)`（去掉 `utm_*` 等跟踪参数与锚点），
  无链接时用 `sha1(源:id|guid)`；全表唯一索引，重复抓同一篇不会翻倍。
- 出处链接统一过 `sanitize.safe_url`，只放行 http(s) 与站内路径。
- 自动抓取**只适合单实例**：多副本会各自抓一遍。要扩容就把间隔设为 0，改由外部定时任务
  打 `POST /news/refresh`（需 `data:write`）。

### 低：文档与前端细节

- 顶栏新增「市场消息」（所有只读用户可见）与「消息源」（`data:write` 可见）两个入口。
- **默认落地页改为市场消息**：导航顺序是「市场消息 → 参数对比」，`/` 直接跳到 `/news`，
  登录后的默认 `next`、站内跳转兜底、403/500 页的返回链接也一并指向 `/news` ——
  普通账号只有 `data:view`，一登录就能看到友商动态，不用先面对参数对比的型号选择器。
- `app/static/news.js` 零依赖实现单列时间线：无限滚动的新卡片按 `data-day` 接到对应日期组末尾
  （一页可能从某天中间开始，服务端预先分组会重复日期头），组头点击折叠并同步 `aria-expanded`。
  DOM 顺序仍是时间倒序，Tab 与读屏顺序正确；**不做多列瀑布流**——倒序时间线拆到多列后视线要来回跳，
  而 CSS `columns` 是列优先填充，会把倒序读成「先左列到底、再右列」。
- README 补「市场消息看板」整节（数据链路、为什么游标分页、为什么没上 React 组件库），
  「暂未实现」收敛为「客户侧消息源 / 消息全文抓取 / 多实例选主」。

## 升级注意事项

- 升级前备份数据库与 `datasheets` 原文目录（本版新增两张表，备份是固定动作）。
- 启动日志应出现 `表结构 8 → 9：v9 …`（老库）或 `0 → 9`（全新库），以及 `[startup] 预置 11 个内置消息源`（仅首次）；
  随后会看到后台回填日志 `[news] 原文链接解析：补了 N 条`。
- 外网不可达的环境里，源会全部记成失败状态但不影响看板启动；看板页会显示空状态。

```bash
git pull --ff-only
docker compose pull
docker compose up -d
docker compose logs -f app
```
