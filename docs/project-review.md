# 项目全面审查与优化记录

审查日期：2026-11-03。仓库：kid941005/competitive-board。基于本地 main / d34706a 及工作区内容。

本次直接修复已确认的安全、数据一致性、功能及异常边界问题，并补充回归测试。
开始审查时已有 38 个受版本控制文件的未提交修改，以及 entity_names、references、uploads
三个新增模块；这些内容被保留并参与验证，不把它们全部归为本轮新增成果。

## 1. 范围与结论

检查覆盖应用装配、登录与权限、页面及机器 API、对比计算、公司/型号/客户采用管理、
CSV/XLSX/JSON 导入、规格书解析和提交、导出与业务备份、来源引用清理、审计与保留策略、
数据库迁移、MCP 适配、模板和原生 JavaScript、容器入口、Compose、CI 与部署文档。

当前 FastAPI + SQLModel + Jinja2 + 原生 JavaScript 的单体架构适合单团队的参数管理与对比。
已有共享的单位、数值、名称归一、客户采用、矩阵组装和来源引用服务，依赖方向基本合理。
优先修复公共边界并收敛重复规则，比更换框架更能提高当前项目的可靠性。

实现范围内的主流程有可执行测试：空库启动 → 应用指标字典 → 建档/导入 → 人工复核 →
查询/对比/溯源 → 导出；权限、失败响应、删除子记录与来源清理、幂等与预演同样经过验证。
PDF 主流程此前存在真实故障，已经用实际生成的 PDF 上传测试验证修复。

新闻动态、网页自动采集、多条件参数透视、趋势视图、细粒度数据域权限仍是 README
列出的未实现功能。它们属于后续产品范围，本轮没有把部署草稿视为已经实现，也没有
扩建这些大型业务。若验收目标包含这些功能，应分别制定需求和交付测试。

## 2. 高严重度：安全或数据/核心功能风险，已修复

| 问题 | 触发与影响 | 修改与验证 |
|---|---|---|
| Cookie API 写入缺少 CSRF 校验 | 已登录浏览器可直接 POST/PATCH/DELETE `/api/v1`，包括令牌签发和吊销，缺少浏览器写入边界保护 | 在 `require_scope` 中统一校验 Cookie 主体的写请求；Bearer 保持机器调用方式。测试无头/错误头 403、正确头和 Bearer 成功 |
| 规格书提交结果中的未转义 HTML | 新公司/型号名称被拼入 `parts.join` 后写入 `innerHTML`，可能把名称当成 HTML 执行 | 对整段动态结果做 HTML 转义；其他结果字段继续使用原有转义函数 |
| PDF 被当作纯文本解析 | 上传临时文件是 `.pdf.tmp`，解析器仅判断 `.pdf` 后缀，导致 PDF 提取流程无法可靠工作 | 识别临时后缀后的原始类型；真实 PDF 上传提取 `0.7 L/min → 700 mL/min`，损坏 PDF 返回 422 |
| PDF 依赖升级导致原生崩溃 | `pymupdf>=1.24` 接收 2.x；本机 2.0 自动加载布局/ONNX 推理栈，在导入时 access violation | 固定到实际验证的 `pymupdf==1.26.7`，本地依赖同步并通过 PDF 回归；后续升级须重跑 PDF 测试 |
| 合并旧库型号时未迁移客户采用关系 | 去重删除被采用关系引用的型号，可能使迁移失败，未强制外键的旧库还可能留下悬空引用 | 删除前迁移采用关系，同客户冲突保留赢家记录；启用 SQLite 外键的旧库迁移测试通过 |
| 型号去重删除内部空格 | 迁移按删除所有空白后的型号分组，但数据库约束仅忽略大小写与首尾空格，`A1` 与 `A 1` 会被误合并 | 与唯一索引口径对齐，仅 strip/lower；测试保留两个不同型号 |

## 3. 中严重度：一致性、异常处理和功能边界，已修复

| 问题 | 修改内容 | 结果 |
|---|---|---|
| 增量分页只返回时间戳 | 增加时间 + 参数 ID 的二元 `cursor`，返回 `next_cursor`/`has_more`；保留 `next_since` 兼容字段 | 同一更新时间下超过页大小的条目可以前进，无重复卡页；文档和 MCP 清单同步 |
| ETag 漏掉关联对象及参数字段 | 对完整、稳定排序的产品表示计算指纹，不再维护手工字段列表 | 公司名称、来源、置信度、更新时间、采用关系等响应变化都会更新版本 |
| PATCH 产品详情与 GET 字段不同 | 新增统一 `_product_payload`，GET、PATCH 和版本检查共用 | PATCH 返回 specs、missing_metrics、完整度及采用关系；GET/PATCH 数据和 ETag 一致 |
| API 路由 404/405 不走统一信封 | 注册 Starlette HTTPException 处理器，并限定 `/api/v1` 的准确路径边界 | 路由级 404/405 同样返回 `{ok:false,error,meta}` |
| 非有限数的校验错误再次触发 JSON 异常 | 错误详情中的 NaN/Infinity 转为可序列化文本 | 非法数字返回稳定 422，而不是在错误处理器中变成 500 |
| 非 ASCII CSRF 值抛 TypeError | 用 UTF-8 字节比较 CSRF 值 | 非法表单令牌统一拒绝，避免非 ASCII 文本引起 500 |
| 比较 ID / 导入行号解析边界 | 拒绝 Unicode 伪数字和过长 ID；行号仅接受长度受限的 ASCII 十进制文本 | `²`、超长数字等输入不会在 int 转换时崩溃 |
| 令牌有效期无范围 | API 和共享服务限制 1–3650 天；页面保留 0 表示长期，非法表单显示原因 | 负数、超大值和非法天数不会创建立即过期令牌或触发 datetime 溢出 |
| MCP 请求结构错误使服务退出 | 校验 JSON-RPC 版本、method、id、params、工具名和 arguments；通知不返回响应 | 错误请求返回 -32600/-32602，随后 ping 仍可处理 |
| MCP 重试/版本保护参数无法传递 | 支持工具参数 `idempotency_key`/`if_match`，映射到 HTTP 请求头，并校验头值 | 支持幂等的工具可重试；产品修改可携带版本，服务端契约与客户端文档一致 |
| 同内容上传共用临时文件 | 每次上传使用 UUID 临时文件；先原文后元数据发布，失败清理临时文件 | 消除并发上传对同一临时路径的争用；存储不可用返回 503，解析失败返回 422 |
| 文档元数据缺失/损坏未处理 | 严格 doc_id fullmatch，校验元数据结构、扩展名及原文存在 | 缺失或损坏的文件不能被继续提交成有效来源 |
| Excel/CSV 把文本当作公式 | 提取共享 export_safety；Excel 使用显式文本单元格，CSV 对危险文本加文本前缀 | 公式形态文本不会作为公式导出；Excel 原文本仍可读回，普通负数保留 |
| 非法 XML 字符使 Excel 导出失败 | 写入 Excel 前替换 XML 禁止的控制字符及非法码位 | 含控制字符的业务文本也可导出；这类字符替换为 `�`，正常文本原样保存 |
| 多值单元格绕过单位换算 | 导入保留“只取第一个值”的人工确认提示，同时继续按单位换算 | `0.7 L/min / 0.9 L/min` 首值落成 700 mL/min，避免提示虽出现但值差 1000 倍 |
| 单位换算溢出 | 共享转换函数拒绝非有限输入和溢出结果，数值/范围解析也拒绝超界值 | 不把 Infinity 写入数据库或返回响应 |
| 空库测试依赖其他文件先建表 | 清理测试业务表前初始化结构 | 独立进程验收中原先失败的 7 个空库用例通过 |
| 错误页返回链接使用未验证 Referer | 仅接受同站 HTTP(S) 来源或安全的站内相对路径 | 避免错误页把 javascript 等值写成可点击返回链接 |
| 前端置信度 0 被默认值覆盖、Infinity 未拦截 | 使用 Number.isFinite，区分 0 与无效值 | 不把 0 自动变成 0.7，不发送非有限参数 |

## 4. 低严重度：结构、命名、文档与工程一致性，已优化

- `api_schemas.py` 独立承载 API 请求模型，路由模块负责协议编排；保留现有 URL 和业务语义。
- 产品详情只有一套表示，矩阵/备份导出共用安全模块，合法浏览器测试共用 CSRF helper。
- API 健康接口通过 `request.app.version` 读取版本，消除反向导入 main 的运行时依赖。
- 修正 `confidential` 等不准确变量名，以及文档中已过时的函数归属和工具数量。
- 容器 CMD 明确 `--no-proxy-headers`；只有启动 uvicorn 且显式配置代理信任范围时，入口才追加代理参数。
- CI Python 与生产镜像统一为 3.12，显式安装 Node 24，并将 scripts 纳入静态检查。
- CI 保留每个测试文件独立进程，改由 pytest 自动收集，避免手写运行器遗漏新增用例。
- 更新 API/MCP 的 CSRF、游标、ETag 和请求头说明；采集栈部署说明明确标记为草稿。
- 修正上传内存说明：分块检查限制累计体积，但返回完整 bytes 仍需要完整文件内存。

## 6. 后续建议与尚存边界

| 优先级 | 建议 | 适用条件 / 原因 |
|---|---|---|
| 中 | 统一所有写通道的数据库级并发版本机制 | 当前 If-Match 检查与写入有时间窗；参数批量写、页面写、导入与采用记录写入也会改变资源。多进程、多副本或多名操作者高频同时写入时，应引入统一版本列/事务锁并增加真实并发测试 |
| 中 | 为增量同步增加删除事件和产品元信息事件 | 当前 changes 是仍存在的参数增量；完整镜像同步需定期全量核对，二元游标没有把该接口扩展成完整 CDC |
| 中 | 增加 PostgreSQL 集成测试与容器启动验收 | SQL 方言兼容不能仅由 SQLite 测试证明，尤其需要验证迁移、唯一索引、事务与并发行为 |
| 中 | 大文件解析移出请求事件循环，必要时引入任务进度 | 当前异步上传路由仍执行同步解析/导入；页数和体积上限限制单次资源，但大文件仍可能影响请求响应时间 |
| 中 | 区分业务导出与完整恢复备份 | Excel 导出不包含登录账号、令牌、全部审计/设置/原文，也不能逐字段恢复参数明细。完整恢复应备份数据库和 datasheets，并演练还原 |
| 低 | 继续按领域拆分 api_v1 路由与写入服务 | 请求模型已分离，但 api_v1 仍较大；下一步可拆 entities/products/specs/adoptions/discovery，保持共享规则与事务边界，不机械复制模块 |
| 低 | 逐步收敛大数据量全表扫描和关联查询 | 当前规模下足够，规模增大后应按请求涉及的产品/来源批量查询，加入代表性性能基准，避免每个请求加载全部骨架 |
| 低 | 为其余依赖增加可复现锁文件与升级流程 | PDF 版本已固定，其余依赖仍是范围；应在支持的平台固定解析结果，并用自动升级 PR 触发验收 |
| 低 | 改善维护脚本的命令行错误提示 | align-entity-meta.py 对缺少 CIB_TOKEN 和首次 API 错误仍可能输出 traceback；建议改为参数检查与稳定退出码，不自动调用生产实例 |
| 产品需求 | 新闻、采集、趋势、多条件和数据域权限分别立项 | 这些在 README 中仍明确未实现，不能用架构接口或部署草稿替代功能验收 |
